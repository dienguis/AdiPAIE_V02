1. NOUVEAU : Action "Rattraper acquisitions" (plage de mois)
================================================================================

Cas d'usage metier : bascule vers SunuPaie en cours d'annee.
Les salaries n'ont jamais recu les acquisitions mensuelles automatiques des
mois precedant la bascule. Resultat : les soldes sont a 0 (ou negatifs si des
conges ont ete pris et saisis manuellement).

L'action "Acquis. mensuelle" existante ne traite que le mois courant (idempotent).
Pour un salarie vierge en octobre, elle credite seulement +2j au lieu des +20j
cumules depuis janvier.

Solution : nouveau bouton "Rattraper acquisitions" sur ListView SoldeConge.
Popup demande la plage (Mois/Annee debut + Mois/Annee fin). L'action boucle
mois par mois et appelle AcquerirTousSalaries pour chaque, de maniere idempotente.

Resultat teste en local (13/10/2026) :
  - Avant : diop Modou solde = -24,00 (0 acquis, 24 pris)
  - Rattrapage janvier a septembre 2026 (9 mois)
  - Apres : diop Modou solde = -6,00 (18 acquis, 24 pris)
  - Fatou NDIAYE solde = +18,00 (nouvelle beneficiaire)
  - Total : 18 acquisitions creees, 0 ignorees, 0 erreur

Rapport detaille mois par mois dans le message de confirmation
(ex. "01/2026 : 2 cree(s), 0 ignore(s)...").

Fichiers crees :
  - AdiPAIE_V02.Module/NonPersistent/RattraperAcquisitionsRequest.cs (DTO popup)

Fichiers modifies :
  - AdiPAIE_V02.Module/Controllers/SoldeCongeController.cs
    (ajout PopupWindowShowAction dans AcquisitionMensuelleController)
  - AdiPAIE_V02.Module/Module.cs
    (enregistrement du DTO dans AdditionalExportedTypes)

Idempotent : relancer l'action deux fois sur la meme plage ne cree rien de nouveau
(AcquerirMensuel verifie la presence d'un MouvementSolde AcquisitionMensuelle
sur le mois en cours).

7. V1.12 - Mode NetCibleMois (gross-up iteratif) + fix ordre sections bulletin
================================================================================

A - Nouveau mode GratificationBaseCalcul.NetCibleMois
----------------------------------------------------------
Permet au RH de saisir "N mois de net" et de laisser le systeme calculer
le brut necessaire pour que le salarie recoive exactement ce montant net
sur son bulletin cible.

Formule :
  Base          = BrutSocial - cotisations sal. - IR - TRIMF (dernier bulletin valide)
  NetCible      = Base x Multiplicateur (= nombre de mois)
  MontantCalcule = gross-up iteratif (Newton-Raphson) sur IR annualise
                   jusqu'a |NetGain - NetCible| < 1 FCFA

Hypotheses :
  - Cotisations sociales (IPRES RG+RC) deja plafonnees (marginal = 0)
  - TRIMF constante (forfait mensuel invariant)
  - Bareme IR progressif annualise avec reduction famille du salarie
  - Convergence 2 a 4 iterations typiquement

Validation metier : correspond au calcul Excel manuel RH ELTON
(ex. Abdoulaye DIENG, Multiplicateur=2 : Brut gratif ~10 552 000 FCFA
pour 6 014 746 net additionnel cible).

Fichiers modifies :
  - Domain/DomainEnums.cs (enum GratificationBaseCalcul : NetCibleMois = 3)
  - BusinessObjects/Gratification.cs (tooltip)
  - Services/BrutRecurrentService.cs (GetDernierNetReglementaire)
  - Services/GratificationService.cs (cas NetCibleMois + GrossUpVersBrut)
  - wwwroot/help/primes-13mois.html (documentation 4e mode)

B - Fix ordre d'affichage des sections dans le DetailView Bulletin
----------------------------------------------------------
Bug : les sections apparaissaient dans l'ordre
  Salaire brut -> Autres Retenues -> Cotisations Sociales -> Retenues Fiscales
au lieu de l'ordre reglementaire du bulletin PDF
  Salaire brut -> Cotisations -> Retenues Fiscales -> Autres Retenues.

Cause : les 4 GroupeImpressionRef avaient OrdreGroupe = null, le tri se
faisait sur Libelle alphabetique ("Autres" < "Cotisations" < "Retenues" < "Salaire"
mais Salaire etait traite a part).

Fix : SeedService force OrdreGroupe = 10 / 20 / 30 / 40 lors du seed.
Au prochain demarrage, les sections affichees sont bien triees.

Fichiers modifies :
  - Services/SeedService.cs (overload EnsureGroupe avec parametre ordre)

Pas de migration SQL requise (le champ OrdreGroupe existe deja, le seed
le remplit automatiquement).

6. FIX V1.11.1 : TRIMF_Mois / IR_Mois / IPRES_*_Mois desynchronises
================================================================================

Bug observe prod (bulletin Alpha Maalik DIA 06/2026) :
  - Colonne "TRIMF (mois)" dans ListView : 0
  - Ligne TRIMF du bulletin : 3 000
  Incoherence entre champ synthetique et ligne detaillee.

Cause racine : UpdateSyntheseFiscale() utilisait Session.Evaluate sur
BulletinLigne qui ne voit pas les modifications en memoire (dirty) des
lignes modifiees juste avant par CalculerTRIMF_Baremise / CalculerIPRES_CSS /
CalculerIRPP. Le SELECT SUM retournait l'etat avant modification.

Meme pattern que le bug corrige en V1.8.1 pour BrutFiscal_CumulAnnee /
BrutSocial_CumulAnnee / NetAPayer_CumulAnnee, mais oublie pour les champs
TRIMF_Mois, IR_Mois, IPRES_RG_Mois, IPRES_RC_Mois et leurs CumulAnnee.

Correctif : UpdateSyntheseFiscale calcule :
  - _Mois via LINQ sur la collection Lignes en memoire (voit les dirty)
  - _CumulAnnee via XPQuery sur autres bulletins (voit dirty si charges)
                + valeur _Mois du bulletin courant

Fichier modifie :
  AdiPAIE_V02.Module/BusinessObjects/Bulletin.cs (UpdateSyntheseFiscale)

Impact utilisateur : apres rebuild + "Recalculer cotisations" sur un bulletin,
les 8 colonnes synthetiques de la ListView Bulletins sont immediatement
synchronisees avec les lignes du bulletin.

Pas de migration SQL requise (les champs persistes existent deja).
